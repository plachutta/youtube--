Claim verifier - basic verification

## Provider-neutral engineering task acceptance

Use `engineering-task-verifier.js` with the canonical task contract from `utils/engineering-agent-runtime.js`. Each acceptance criterion must declare either an allowlisted deterministic command or an explicit human-review owner. The verifier executes command checks independently with `execFile` (no shell), a per-check timeout, bounded output, observed exit status, and SHA-256 evidence references. Human review remains `blocked`; no agent result may set acceptance.

The existing `verifier.py` and its `data/` outputs are a legacy placeholder, not a qualified engineering claim verifier: `check_evidence()` currently returns `true` unconditionally and its fixed output path is workspace-specific. Do not cite that legacy script as qualification evidence until it is independently repaired and tested. The new task verifier does not modify or overwrite its historical outputs.

## Adversarial qualification

Run the verifier's dedicated local suite with `node tools/claim-verifier/tests/claim-verifier.test.js`. It builds disposable fixtures under the operating-system temp directory and removes them afterward; it does not execute the legacy Python verifier or write to its historical `data/` outputs. The verifier uses a reviewer-owned criterion policy and command-ID allowlist, freshly executed in-memory receipts, direct file/hash checks, and separate human-review records. A PASS from the fixture suite qualifies only the covered verifier behaviors; it does not qualify visual quality or production readiness.

For `kind: test`, the verifier-owned policy must pin `expectedSha256` for the approved test source and its allowlisted Node command must directly invoke that relative test path (`node path/to/test.js` or `node --test path/to/test.js`). Do not derive the expected hash from the implementation claim or accept an eval/wrapper command as proof the test ran. For `kind: render`, a PASS establishes only the configured command receipt plus fresh manifest/artifact and byte-hash consistency; it does not establish playable media, genuine renderer execution, or subjective visual quality. Require a separate trusted human-review criterion where visual acceptance is required.

## Roadmap acceptance states

`validateRoadmapFile()` returns separate `structuralStatus`, `traceabilityStatus`, `semanticStatus`, and `ownerAcceptance` values. A structurally valid and internally linked roadmap returns `status: REVIEW_REQUIRED`; neither section headings, hashes, deliverable categories, nor the traceability graph establish semantic adequacy. The graph is generated from the actual roadmap hash and stage sections; its links are source-bound stage-exit traceability, not a claim that natural-language criteria are objectively sufficient. A claim bundle cannot supply this policy graph.

Use `createCanonicalRoadmapVerifier()` as the canonical roadmap acceptance entry point. It loads the verifier-fixed, source-hash-pinned reviewer registry and traceability graph. Direct `ClaimVerifier` construction with any nonempty human-review key registry is rejected (`UNTRUSTED_REVIEWER_POLICY`); direct roadmap semantic/owner policies are also rejected (`UNTRUSTED_ROADMAP_POLICY`). Caller-supplied request keys, signatures, records, or policy objects cannot establish reviewer trust. The canonical registry currently has zero trusted reviewers; therefore there is no supported human-acceptance PASS path in this environment. A source-pinned repository file is only a trust anchor relative to an independently trusted verifier source; because the verifier is currently untracked and there is no external owner key/configuration, this does not establish an external trust root. For a future overall roadmap `PASS`, the separately authorized verifier policy must link two required human criteria: `semantic_review` by a trusted `independent_reviewer`, and `owner_acceptance` by a trusted `product_owner`. Each record must bind the current complete artifact SHA-256 and exact required criterion IDs with structured observations. A missing review yields `REVIEW_REQUIRED`; a claimed acceptance with missing, stale, malformed, untrusted, wrongly scoped, or invalidly signed evidence yields `FAIL`. A valid signature authenticates a key’s signed statement, not the thoughtfulness of the person’s review.
